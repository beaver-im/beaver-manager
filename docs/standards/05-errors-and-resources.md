# 第6章　错误处理、日志与资源清理

## 6.1 错误不被吞掉

**当前事实**：请求封装在 `code !== 0` 时不会自动弹窗，而是把响应原样交给调用方；网络异常以 rejected Promise 抛出。认证失败是封装层唯一直接跳登录的分支（见[第5章](04-auth-and-routing.md)）。

**统一约束**：

- API 调用方先判断 `code`，成功再用 `result`；失败用 `msg` 或统一提示，不能把失败渲染成空成功列表。
- `catch` 必须明确处理边界：提示用户、回滚局部状态、记录必要上下文之一；禁止空 `catch` 伪装成功。
- 外部输入（网络响应、`localStorage`、文件、URL 参数）先校验格式；校验失败给出可定位信息，不把原始异常直接暴露给用户。
- 日志不记录 Token、密码、真实用户隐私或完整请求体；需要排障时记录操作标识与错误类别。

## 6.2 资源与生命周期

- 组件内 `setTimeout` / `setInterval`、事件监听、WebSocket 或第三方实例，必须在 `onBeforeUnmount` 中清理。
- 页面切换或搜索条件快速变化时，旧请求结果不得覆盖新状态；用请求标识或取消机制隔离。
- 弹窗、抽屉关闭时清理草稿与校验错误，避免下次打开残留上一次状态。
- 资源文件改名后，所有引用同步更新；不保留旧文件副本“以防万一”。

## 6.3 评审检查

- 每个失败分支是否可见、可恢复；是否把 `code !== 0` 当成功？
- 是否有空 `catch`、裸 `any` 异常或把服务端原文直接当提示？
- 监听/定时器/请求是否在销毁或条件变化时释放？
- 日志是否脱敏；是否留下旧文件名/旧接口的兼容兜底？
